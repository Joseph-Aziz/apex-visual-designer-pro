# Release 1.3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship plug-in version 1.3.0 with docs that match the product, a checklist run on a fresh install, and a roadmap that replaces the old-repository plan.

**Architecture:** No new product features. The work is release hygiene: a release-prep change (already edited, not committed), a small Node helper that turns the SQL test files into blocks SQL Commands can run, the clean-install checklist filled in on the live instance, two documentation reconciliations, a roadmap, and the tag.

**Tech Stack:** plain browser JavaScript, Node `vm` unit tests, Oracle PL/SQL, APEX 26.2 SQL Workshop in the browser pane.

**Spec:** none. The review that produced this plan is summarised in the Roadmap task (Task 6).

## Global Constraints

- Repository `E:/apex-visual-designer-pro` on branch `main`. Do not touch `E:/apex-visual-designer-plugin` (the public repository), the pilot application, or the pilot schema.
- Commit and push only when the user says so. Each task ends by asking the user whether to commit it. Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- No environment names (workspace, schema, host, user names) in repository files. `tests/unit/no_env_values_test.js` enforces it; run it after every doc change. Do not hardcode the test application or scratch page in repository code; tests take them as `&&TEST_APP` and `&&SCRATCH_PAGE`. The user names both in chat.
- The SQL export comes from the build only: `node tools/build_plugin.js`. Never edit `plugin/region_type_plugin_apex_visual_designer.sql` by hand.
- The user runs compiles and plug-in imports. SQL may be run only through the user's opened SQL Commands in the browser pane, in the schema the user names; that name never goes into a file. Never enter passwords. Never navigate to an application runtime page without a session. No App Builder deep links.
- Do not change application security or authentication settings.
- Keep old behaviour out: fix forward, never restore a removed behaviour.
- Chat with the user in caveman style; code, docs and commits in normal prose.

- `db_test_block.js` must leave `&&` sequences that are not the three known names untouched, and must not split on a `/` inside a string.
- A checklist FAIL is fixed in the owning file with a failing test first, then that check is run again.

### Task 2: SQL test block helper

**Files:** Create `tools/db_test_block.js`; Test `tests/unit/db_test_block_test.js`; Modify `README.md` (one line under Tests).

**Interfaces:** `node tools/db_test_block.js <tests/db/file.sql> <schema> <app> <page> [--out <dir>]` prints, or writes as `<name>_<n>.sql`, one runnable block per statement for APEX SQL Commands. Exposes `module.exports = { blocks(sqlText, { schema, app, page }) -> string[] }` for the test.

Rules of `blocks`:
- `&&VD_SCHEMA.` becomes `<schema>`; `&&TEST_APP` becomes `<app>`; `&&SCRATCH_PAGE` becomes `<page>`. Any other `&&NAME` stays as it is.
- Lines that start with `SET `, `DEFINE `, `PROMPT ` or `@` (case-insensitive, after optional spaces) are dropped.
- The text is split on a line that is exactly `/`. A `/` inside a line, string or comment is not a split.
- Empty blocks are dropped; each block is trimmed.

- [ ] **Step 1: Write the failing test.** Load the module with `require`. Assert: the three substitutions; `&&OTHER` kept; `SET`, `DEFINE`, `PROMPT`, `@@tables/x.sql` lines dropped; `'a/b'` inside a line does not split; a text with two `/` lines gives two blocks; a trailing `/` gives no empty block.
- [ ] **Step 2:** Run `node tests/unit/db_test_block_test.js`. Expected: FAIL, module missing.
- [ ] **Step 3:** Implement with Node `fs` and `path` only. When run as a script, print blocks separated by a line `-- block N --`, or write files with `--out`.
- [ ] **Step 4:** Run the test and `node tools/db_test_block.js tests/db/layout_tests.sql X 1 2 | head`. Expected: PASS, and the first block starts with `DECLARE` or `BEGIN`.
- [ ] **Step 5:** README, under Tests: "`node tools/db_test_block.js tests/db/<file>.sql <schema> <app> <page>` prints the file as blocks for SQL Commands."
- [ ] **Step 6:** Run all unit tests. Ask the user to commit: `feat: print a SQL test file as SQL Commands blocks`.
