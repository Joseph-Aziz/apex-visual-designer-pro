# APEX Visual Designer: brief for the visual designer

This folder holds static copies of the four screens of the APEX Visual Designer editor:

| File | Screen |
|---|---|
| `1-design-items.html` | Design items: the component list on the left, the live page preview in the middle, and a gallery of looks for the selected component on the right |
| `2-theme-designer.html` | Theme Designer: styles that apply to the whole application |
| `3-layout.html` | Layout: move and resize the boxes of a page |
| `4-theme-styles.html` | Theme styles: saved looks that can be reused on any page |

Every screen uses the same stylesheet, `editor.css`. Open any HTML file in a browser. No server is needed.

## Your freedom

You may redesign how the editor looks and is arranged. Change the HTML and the CSS as you see fit:

- **Page structure:** move, merge, split or reorder panels, bars and sections.
- **Menus and navigation:** regroup buttons, put actions into menus, tabs, drawers or toolbars, and change the side rail.
- **Look:** colours, fonts, spacing, icons, cards, buttons, inputs, states and motion.
- **Wording:** propose clearer labels and help text.

What does not change is what the editor does. Every button, field, list and setting must still exist somewhere, so that it can do the same job. The developer rebuilds your HTML in the application's code and wires the existing functions to it.

## The few rules

1. **Keep the hooks on each working element.** The code finds an element by its `class`, `id`, `data-*` and `aria-*` attributes.
   - Keep those attributes on the element, wherever you move it.
   - Keep the element's kind: a button stays a `<button>`, an input stays an `<input>`, a select stays a `<select>`.
   - You may add your own classes and wrapper elements freely.
2. **Do not remove a function.** You may hide a rarely used action behind a "More" menu. You may not drop it.
3. **Mark your structure changes** with a short HTML comment, so the developer finds each one fast. For example:
   ```html
   <!-- CHANGED: Save to page moved into the right panel -->
   ```
4. **Repeated items are generated by code.** Lists (components, gallery cards, settings, styles) are built from data. Design one item well, and the rest follow the same markup.
5. **Leave the page preview alone.** The white panel in the middle of Design items is the user's own APEX page. Design its frame, not its content.
6. **Keep the colour tokens.** The variables at the top of `editor.css` (`--...`) are the palette. Change their values or add new ones.
7. **Accessibility:**
   - text contrast at least 4.5:1;
   - a visible focus outline on everything you can click;
   - click targets at least 32px high.
8. **Right-to-left.** The editor also runs in Arabic. Use logical CSS properties:
   - `margin-inline-start`, not `margin-left`;
   - `padding-inline-end`, not `padding-right`;
   - `inset-inline-start`, not `left`.
9. **No external files.** Do not link fonts, images or CSS from a CDN. A font must be a system font or one we can ship with the plug-in; name it in your notes.

## What to send back

- `editor.css`, updated.
- The four HTML files, updated, with your `CHANGED` comments.
- `NOTES.md` (optional), covering:
  - anything the static files cannot show, such as hover flows, menus opening, or a screen on a phone;
  - any font you used;
  - screenshots or sketches of the intent.

## Things worth knowing

- Users found the editor complicated. The main goal is clarity:
  - which actions write to the live application (Save to page, Publish theme, Apply to page);
  - which actions only keep a draft (Save draft, Save as theme style).
- The yellow strip under each title is a one-line help message. The user can close it.
- The dialog that asks before a live write (class `vd-ask`) does not appear in these static files. Its styles are in `editor.css` under `.vd-ask`; you may redesign it as well.
